# 换桩收件核销服务（recon）

接入 `source_service.py` 的两家运营商日账、施工分表读数与会计交接台，做一个**可跨轮次、
跨进程重启持续工作**的收件核销端。只依赖 Python 3.11 标准库。

## 运行

```sh
# 终端 A：来源联调服务
python3 source_service.py --port 8040

# 终端 B：每个轮次（shift）调用一次 run；状态全部落在 --state 目录
python3 -m recon.cli --base http://127.0.0.1:8040 --state ./recon_state run

# 值班员视图：站日/分表完整度、待追证据、可核销量、会计交接状态
python3 -m recon.cli --state ./recon_state status

# 会计/值班员人工确认一笔待处理调账（审批签发后才允许）
python3 -m recon.cli --state ./recon_state adjust EAST 2026-11-20

# 测试
python3 -m unittest discover -s tests -v
```

`run` 可安全重复调用：归档 token 幂等、会计请求号幂等、游标/回条/读数修订全部落盘，
重启后从同一状态目录继续，不重复申请归档、不重复发送已确认用量。

## 模块划分

| 文件 | 职责 |
| --- | --- |
| `recon/client.py` | 来源服务 HTTP 客户端，把 4xx/5xx 统一成 `SourceError`，连接错误保守重试一次 |
| `recon/store.py` | 单一 JSON 状态文件 + 原子替换；归档分片内容缓存与摘要 |
| `recon/amounts.py` | 定点电量（Decimal）、两位小数量化、时分区间工具 |
| `recon/ledger.py` | 版本化资料解释、片段归类、三桶归集、来源判定（纯领域逻辑，可单测） |
| `recon/engine.py` | 一轮收件的编排：日账/流水/归档/读数采集 → 核销 → 会计交接状态机 |
| `recon/cli.py` | `run` / `status` / `adjust` 命令行 |

## 关键业务规则如何落地

### 日账完整性：只认真实末页/封账/归档清单，禁止拼接

- **旧运营商**：按 `edition + cursor` 翻页，只有同一修订读到 `next=null` 才置完整。
  遇 `409`（游标随修订失效）丢弃本修订已读页、回到新版首页重读，**绝不跨修订拼页**；
  遇 `410`（转归档）标记过期，即使手里有完整实时快照也改追归档权威清单。
- **新运营商**：按入账序消费变化流水。封账 `seal.through` 只与该日的**事实事件**
  （record/retract）比较；封账之后到达的撤回/补交使旧封账失效。遇 `410` 压实，记录
  `floor` 与受影响营业日，这些日期只能靠日包确认，不拿残留事件声称完整。
- **归档**：每轮一个新申请名额；同 `operator/day` 用稳定 token 幂等申请，重启后能查回
  已申请任务。包 `ready` 且目标日全部分片通过 **sha256 + 行数**核对后，才以归档版确认
  该日。相邻营业日不能靠本包清单确认，也不提前领取其分片（“可只领需要的分片”）。
- 归档版到达后整体覆盖实时视图；撤回的账片从有效集合剔除。

### 归枪 / 共表 / 无法确认三桶

每个分表窗口输出三个量，核销人员可清楚区分：

- `attributed`：有确定性施工单（表号+装表世代+窗口匹配且完整覆盖区间）或账片自带 split
  独立表端明细，能归到具体枪位的用量；
- `meter_only`：只能确认在共表上的余量 = 同世代首末累积之差 − 已归枪 − 无法确认部分，
  **绝不拿共表余额反推每支枪**；
- `unconfirmed`：缺读数、总量对不平，或接线时间落在 `interval_uncertain` 闭区间且无独立
  表端明细的片段。旧表清零与新表读数属不同装表世代，读数出现负差即判口径异常、不相减。

`chase` 字段逐条回答“剩余电量还要向哪家追单”（运营商、账片号、时段、电量、原因）。
一家档案未发齐不阻塞另一家已对清的分表：`close.json` 中 `independent` 的 EAST 只要求
legacy，截账轮即可先交。

### 桥接凭据

只有 `state=active` 的桥接能把两个来源片段归为一次交易；桥接撤回后只拆开对应那笔，
不按内容相似度自动合并、不把 m17 与 n41 重新凑成交易。`status.bridges` 保留每次凭据的
active/withdrawn 可追溯状态。

### 会计交接状态机

- 状态区分 `unknown`（回条断开，会计收没收到未知）/ `received`（已接件待确认）/
  `posted`（已过账）/ `returned`（退回，带 `check` 时段）。
- 送件遇 `503`：登记 `in_flight`，下轮**先 `GET /account/result`**；404 才用完全相同的
  请求号与内容重发，查到回条则只更新状态、不重发，避免已确认用量送两次。
- 同一请求号始终同内容；已 `posted` 的金额与来源版本冻结，仍按原交接单查询。
- 后到的读数更正只生成 `pending_adjustments` 可追溯差额（旧版/新版/差值/审批号），
  审批未签发前 `adjust` 拒绝发送；人工确认后凭审批号 + 原请求号送 `adjustment` 调账。
- 会计退回（如 OLD 的 11:20、11:30 时段）保留 `check`，交核销人员按指定片段补收。

## 状态目录

```
recon_state/
├── state.json        # 轮次、游标、事件、归档任务、读数修订、交接状态、运行日志
└── content/          # 已核对摘要的归档分片（NDJSON 原文）
```
